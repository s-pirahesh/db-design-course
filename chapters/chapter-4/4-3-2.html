🔷 حالت 5: ارتباط بازگشتی 1:N

قاعده

یک موجودیت با خودش ارتباط 1:N → 1 رابطه 

E ──1:N── E
→ 1 جدول: E + FK به خودش

نکته مهم: حتماً Rename + FK به خودش!

مثال 1: سازمان - کارمند و مدیر (Boss)

نمودار ER: 

N              1
   Employee ──مدیر── Employee
erDiagram
    EMPLOYEE ||--o{ EMPLOYEE : "manages"
    
    EMPLOYEE {
        int EmpID PK
        string Name
        int Age
        int BossID FK
    }

نگاشت: 

-- فقط یک رابطه!
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Age INT,
    BossID INT,  -- FK به خودش! (Rename شده)
    FOREIGN KEY (BossID) REFERENCES Employee(EmpID)
);

-- نماد:
Employee(EmpID, Name, Age, BossID)
         ------              ......
                               ↓ FK به خودش!

داده نمونه: 

+-----+--------+-----+---------+
| EID | Name   | Age | BossID  |
+-----+--------+-----+---------+
| 100 | رضا    | 45  | NULL    |  ← مدیر کل (بدون Boss)
| 110 | علی    | 35  | 100     |  ← مدیرش رضا است
| 120 | سارا   | 30  | 100     |  ← مدیرش رضا است
| 130 | مینا   | 28  | 110     |  ← مدیرش علی است
| 140 | حسین   | 26  | 110     |  ← مدیرش علی است
+-----+--------+-----+---------+

نمودار سلسله‌مراتب: 

رضا (100)
         /    \
    علی (110)  سارا (120)
     /    \
مینا (130) حسین (140)

تحلیل: 

یک کارمند (Emp=100):
→ چند زیردست دارد؟ → N زیردست ✅

یک کارمند (Emp=110):
→ چند مدیر دارد؟ → 1 مدیر ✅

→ 1:N ✅

Query‌های مفید: 

-- زیردستان یک مدیر
SELECT E.Name AS Employee
FROM Employee E
WHERE E.BossID = 100;  -- زیردستان رضا

-- مدیر یک کارمند
SELECT B.Name AS Boss
FROM Employee E
JOIN Employee B ON E.BossID = B.EmpID
WHERE E.EmpID = 110;  -- مدیر علی

-- همه کارمندها با مدیرشون
SELECT E.Name AS Employee, B.Name AS Boss
FROM Employee E
LEFT JOIN Employee B ON E.BossID = B.EmpID;

نکات مهم حالت 5 (بازگشتی 1:N)

✅ نکته 1: فقط 1 جدول (خودِ موجودیت)

✅ نکته 2: حتماً Rename برای FK → نمی‌شه EmpID, EmpID داشت!

(چون EmpID و BossID همان دامنه‌اند)

  1. حلقه یا دور (Cycle) ارجاع!

❌ خطا: ساختن جدول جداگانه برای ارتباط!

🔷 حالت 6: ارتباط بازگشتی 1:1

قاعده

یک موجودیت با خودش ارتباط 1:1 → 1 یا 2 رابطه 

E ──1:1── E
→ بستگی به مشارکت دارد:
  - اگر یک طرف الزامی → 1 جدول
  - اگر هر دو طرف اختیاری + درصد کم → 2 جدول
  - اگر هر دو طرف الزامی → 1 جدول

مثال 1: دانشجو - هم‌اتاقی (حداقل یک طرف الزامی)

نمودار ER: 

1              1
   Student ──هم‌اتاقی── Student

نگاشت - حالت 1 جدول: 

CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50),
    RoommateID INT UNIQUE,  -- FK به خودش + UNIQUE!
    FOREIGN KEY (RoommateID) REFERENCES Student(StudentID)
);

-- نماد:
Student(StudentID, Name, RoommateID)
        ----------       ..........
                            ↓ FK + UNIQUE

داده نمونه: 

+-----+--------+-------------+
| ID  | Name   | RoommateID  |
+-----+--------+-------------+
| 100 | علی    | 110         |  ← هم‌اتاقی علی = سارا
| 110 | سارا   | 100         |  ← هم‌اتاقی سارا = علی (متقابل!)
| 120 | رضا    | 130         |
| 130 | مینا   | 120         |
| 140 | حسین   | NULL        |  ← بدون هم‌اتاقی
+-----+--------+-------------+

نکته مهم: داده‌ها باید متقابل باشن: 

اگر: Student(100).RoommateID = 110
→ باید: Student(110).RoommateID = 100 ✅

این رو با Trigger تضمین می‌کنیم:

CREATE TRIGGER trg_roommate_symmetry
AFTER INSERT, UPDATE ON Student
FOR EACH ROW
BEGIN
    UPDATE Student 
    SET RoommateID = NEW.StudentID
    WHERE StudentID = NEW.RoommateID 
      AND (RoommateID IS NULL OR RoommateID <> NEW.StudentID);
END;

مثال 2: هر دو طرف اختیاری (درصد < 30%)

نمودار ER: 

1              1
   Student ──دوست‌صمیمی── Student
   (اختیاری)      (اختیاری)

نگاشت - حالت 2 جدول: 

-- رابطه 1: Student
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Major NVARCHAR(30)
);

-- رابطه 2: CloseFriend (فقط اگر دوست صمیمی داره!)
CREATE TABLE CloseFriend (
    StudentID INT,
    CloseFriendID INT,
    PRIMARY KEY (StudentID, CloseFriendID),
    FOREIGN KEY (StudentID) REFERENCES Student(StudentID),
    FOREIGN KEY (CloseFriendID) REFERENCES Student(StudentID),
    CHECK (StudentID < CloseFriendID)  -- جلوگیری از تکرار
);

-- نماد:
Student(StudentID, Name, Major)
        ----------

CloseFriend(StudentID, CloseFriendID)
            -------------------------

داده نمونه: 

Student:
+-----+--------+-------+
| ID  | Name   | Major |
+-----+--------+-------+
| 100 | علی    | CS    |
| 110 | سارا   | Math  |
| 120 | رضا    | Phys  |
| 130 | مینا   | CS    |
| 140 | حسین   | Math  |
+-----+--------+-------+

CloseFriend:
+-----+-------+
| SID | CFID  |
+-----+-------+
| 100 | 110   |  ← علی و سارا دوست صمیمی‌اند
| 120 | 140   |  ← رضا و حسین دوست صمیمی‌اند
+-----+-------+

مینا (130) دوست صمیمی نداره → در جدول CloseFriend نیست!

چرا 2 جدول؟ 

درصد مشارکت:
→ فقط 2 از 5 دانشجو دوست صمیمی دارن
→ 40% < 50%

اگر 1 جدول می‌ساختیم:
Student(StudentID, ..., CloseFriendID)
→ 60% NULL ها! ❌

با 2 جدول:
→ فقط داده‌های معتبر ذخیره می‌شن ✅
→ Performance بهتر ✅

  • هر دو اختیاری + %<30 → 2 جدول

🔷 حالت 7: نگاشت موجودیت ضعیف

قاعده

موجودیت ضعیف → 2 رابطه 

E (قوی) ──شناسه─── F (ضعیف)
→ 2 جدول:
  1. E
  2. F + FK از E + صفت ممیزه
  
PK(F) = FK + صفت ممیزه

مثال 1: کارمند و مدرک تحصیلی

نمودار ER: 

erDiagram
    EMPLOYEE ||--o{ DEGREE : "has"
    
    EMPLOYEE {
        int EmpID PK
        string Name
        int Age
    }
    
    DEGREE {
        int EmpID FK
        string Level
        string University
        int GradYear
        decimal Mark
    }

ویژگی‌های موجودیت ضعیف:

✅ موجودیت ضعیف (Degree):

  1. استقلال وجودی ندارد
  2. بدون Employee معنی ندارد
  3. صفت ممیزه دارد (Level: دیپلم، لیسانس، ...)
  4. مشارکت الزامی است
  5. ارتباط شناسه (Identifying Relationship)

نگاشت: 

-- رابطه 1: Employee (قوی)
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Age INT
);

-- رابطه 2: Degree (ضعیف)
CREATE TABLE Degree (
    EmpID INT,  -- FK از قوی
    Level NVARCHAR(20),  -- صفت ممیزه (Discriminator)
    University NVARCHAR(50),
    GradYear INT,
    Mark DECIMAL(4,2),
    PRIMARY KEY (EmpID, Level),  -- ترکیب FK + ممیزه!
    FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
        ON DELETE CASCADE  -- حذف کارمند → حذف مدارک
);

-- نماد:
Employee(EmpID, Name, Age)
         ------

Degree(EmpID, Level, University, GradYear, Mark)
       -------------
       ↓ PK = FK + ممیزه
       
       EmpID → FK
       ......

داده نمونه: 

Employee:
+-----+--------+-----+
| EID | Name   | Age |
+-----+--------+-----+
| 10  | علی    | 35  |
| 11  | سارا   | 30  |
+-----+--------+-----+

Degree:
+-----+---------+---------------+------+------+
| EID | Level   | University    | Year | Mark |
+-----+---------+---------------+------+------+
| 10  | BDC     | IAUT          | 1387 | 19   |
| 10  | MSC     | IAUT          | 1390 | 20   |
| 11  | Diploma | Alborz        | 1384 | 20   |
| 11  | BSC     | Sharif        | 1388 | 20   |
| 11  | MSC     | MIT           | 1390 | 20   |
| 11  | PhD     | Stanford      | 1394 | 20   |
+-----+---------+---------------+------+------+
   ↑       ↑
   FK    ممیزه

3 مدرک برای EmpID=11 (سارا)
2 مدرک برای EmpID=10 (علی)

تحلیل: 

یکتایی در کل جدول؟
→ Level به تنهایی یکتا نیست (چند نفر لیسانس دارن)
→ EmpID به تنهایی یکتا نیست (یک نفر چند مدرک)

یکتایی در زیرمجموعه؟
→ در مدارک یک کارمند: Level یکتاست! ✅
→ (10, BDC), (10, MSC) → یکتا ✅
→ نمی‌شه (10, BDC), (10, BDC) داشت! ❌

→ پس PK = (EmpID, Level) ✅

Query‌ها: 

-- مدارک یک کارمند
SELECT Level, University, GradYear
FROM Degree
WHERE EmpID = 11;

-- کارمندان با مدرک PhD
SELECT E.Name
FROM Employee E
JOIN Degree D ON E.EmpID = D.EmpID
WHERE D.Level = 'PhD';

-- حذف کارمند (CASCADE)
DELETE FROM Employee WHERE EmpID = 10;
-- → مدارک EmpID=10 هم حذف می‌شن! ✅

مثال 3: موجودیت ضعیف روی موجودیت ضعیف!

نمودار ER: 

1         N         1         N
Employee ──── FamilyMember ──── MedicalRecord (ضعیف روی ضعیف!)
  (قوی)        (ضعیف)            (ضعیف)
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50)
);

CREATE TABLE FamilyMember (
    EmpID INT,
    MemberName NVARCHAR(50),
    BirthDate DATE,
    PRIMARY KEY (EmpID, MemberName),
    FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

CREATE TABLE MedicalRecord (
    EmpID INT,
    MemberName NVARCHAR(50),
    RecordDate DATE,  -- صفت ممیزه
    Disease NVARCHAR(100),
    Treatment NVARCHAR(200),
    PRIMARY KEY (EmpID, MemberName, RecordDate),
    FOREIGN KEY (EmpID, MemberName) REFERENCES FamilyMember(EmpID, MemberName)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

تحلیل: 

سلسله‌مراتب وابستگی:
Employee (قوی)
   ↓ قوی برای
FamilyMember (ضعیف نسبت به Employee)
   ↓ قوی برای
MedicalRecord (ضعیف نسبت به FamilyMember)

PK:
→ MedicalRecord = (EmpID, MemberName, RecordDate)
→ شامل کلید FamilyMember + ممیزه خودش!

نکات مهم حالت 7 (موجودیت ضعیف)

✅ نکته 1: PK ضعیف = FK + صفت ممیزه

✅ نکته 2: صفت ممیزه (Discriminator):

  • در کل جدول یکتا نیست
  • در وابسته به یک قوی یکتاست

✅ نکته 3: مشارکت ضعیف الزامی است (با دو خط)

✅ نکته 4: ارتباط شناسه (Identifying)

✅ نکته 5: CASCADE DELETE ضروری است!

✅ نکته 6: درجه ارتباط معمولاً 2 است (گاهی بیشتر)

✅ نکته 7: چندی معمولاً 1:N (گاهی M:N)

✅ نکته 8: ضعیف می‌تونه برای ضعیف دیگر قوی باشه!

❌ خطا: فراموش کردن صفت ممیزه در PK!

🔷 حالت 8: نگاشت صفت چندمقداری

قاعده

صفت چندمقداری → جدول جداگانه! 

E با صفت چندمقداری A
→ +1 جدول برای A:
  1. E (بدون A)
  2. E_A (FK + A)

فرمول: اگر n صفت داریم که m تای آن چندمقداری → n+m+1 جدول

مثال 1: کارمند با چند شماره تلفن

نمودار ER: 

┌──────────┐
│ Employee │
├──────────┤
│ EmpID    │
│ Name     │
│ {Phone}  │ ← چندمقداری!
└──────────┘

نگاشت: 

-- رابطه 1: Employee (بدون Phone)
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Age INT
);

-- رابطه 2: EmployeePhone (صفت چندمقداری)
CREATE TABLE EmployeePhone (
    EmpID INT,
    PhoneNumber VARCHAR(15),
    PRIMARY KEY (EmpID, PhoneNumber),
    FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
);

-- نماد:
Employee(EmpID, Name, Age)
         ------

EmployeePhone(EmpID, PhoneNumber)
              -------------------

داده نمونه: 

Employee:
+-----+--------+-----+
| EID | Name   | Age |
+-----+--------+-----+
| 100 | علی    | 30  |
| 110 | سارا   | 28  |
+-----+--------+-----+

EmployeePhone:
+-----+--------------+
| EID | PhoneNumber  |
+-----+--------------+
| 100 | 09121234567  |  ← علی 2 شماره داره
| 100 | 02188776655  |
| 110 | 09359876543  |  ← سارا 1 شماره داره
+-----+--------------+

Query: 

-- تلفن‌های یک کارمند
SELECT PhoneNumber
FROM EmployeePhone
WHERE EmpID = 100;

-- کارمندان با بیش از 1 تلفن
SELECT E.Name, COUNT(*) AS PhoneCount
FROM Employee E
JOIN EmployeePhone P ON E.EmpID = P.EmpID
GROUP BY E.EmpID, E.Name
HAVING COUNT(*) > 1;

نمودار ER:

نگاشت: 

CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50)
);

CREATE TABLE Resume (
    EmpID INT,
    FromDate DATE,
    ToDate DATE,
    Position NVARCHAR(50),
    Department NVARCHAR(50),
    PRIMARY KEY (EmpID, FromDate),  -- From به عنوان ممیزه
    FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
);

نکات مهم حالت 8 (صفت چندمقداری)

✅ نکته 1: هر صفت چندمقداری → +1 جدول

✅ نکته 2: PK = (FK + مقدار صفت)

✅ نکته 3: صفت مرکب + چندمقداری: → همه اجزا در جدول جدید

✅ نکته 4: اگر n موجودیت با m صفت چندمقداری: → n + m رابطه (نه n×m!)

✅ نکته 5: CASCADE DELETE معمولاً می‌خوایم

❌ خطا: گذاشتن چندمقداری در جدول اصلی! مثلاً: Employee(EmpID, Name, Phones) ← ❌ نقض 1NF!
