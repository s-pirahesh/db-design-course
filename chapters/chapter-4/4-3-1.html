🔷 حالت 1: نگاشت موجودیت قوی (Strong Entity)

قاعده

هر موجودیت قوی → یک رابطه (جدول) 

موجودیت E با صفات (A, B, C)
→ جدول E(A, B, C)

📋 قاعده‌هاي تكميلي نگاشت صفات

قبل از سراغ ارتباط‌ها، چند قاعده مهم درباره نگاشت انواع مختلف صفات از ER به رابطه‌اي وجود دارد:

الف) صفت ساده (Simple/Atomic)

صفت ساده مستقیماً به یك ستون در جدول نگاشت مي‌شود. مثال: Name VARCHAR(50).

ب) صفت مركب (Composite)

صفت مركب به چند ستون در همان جدول تبدیل مي‌شود (Flatten). صفت مادر در جدول ذخیره نمي‌شود. 

-- ER: FullName (FirstName + LastName) — مركب
-- RDB:
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    FirstName NVARCHAR(50),  -- جزء مركب
    LastName  NVARCHAR(50)   -- جزء مركب
    -- FullName ذخیره نمي‌شود
);

ج) صفت چندمقداري (Multivalued)

صفت چندمقداري نمي‌تواند در همان جدول قرار گیرد (نقض 1NF). راه حل: ساخت یك جدول جداگانه با PK تركیبي (PK موجودیت + خود صفت). 

-- ER: Student با صفت چندمقداري PhoneNumber
-- RDB:
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50)
);

CREATE TABLE Student_Phone (
    StudentID INT,
    PhoneNumber VARCHAR(15),
    PRIMARY KEY (StudentID, PhoneNumber),
    FOREIGN KEY (StudentID) REFERENCES Student(StudentID)
        ON DELETE CASCADE ON UPDATE CASCADE
);

د) صفت مجازي/مشتق‌شده (Derived)

قاعده مهم: صفت مجازي را ذخیره نمي‌كنیم. این صفت از سایر صفات قابل محاسبه است و ذخیره آن باعث افزونگي و خطر ناسازگاري مي‌شود. 

-- ER: Student با BirthDate (واقعي) و Age (مجازي)
-- ❌ نادرست:
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    BirthDate DATE,
    Age INT  -- ❌ افزونگي! با گذشت زمان، خراب مي‌شود
);

-- ✅ درست: محاسبه در زمان اجرا
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    BirthDate DATE
);

-- در زمان query:
SELECT
    StudentID,
    BirthDate,
    DATEDIFF(YEAR, BirthDate, GETDATE()) AS Age
FROM Student;

-- یا با Computed Column (در SQL Server):
ALTER TABLE Student ADD Age AS DATEDIFF(YEAR, BirthDate, GETDATE());

استثنا: در سیستم‌هاي بسیار پربازدید با محاسبات گران، گاهي صفت مجازي به‌صورت Materialized (با Trigger براي به‌روزرساني) ذخیره مي‌شود؛ اما این یك بهینه‌سازي است نه قاعده طراحي.

🔗 عملیات‌هاي FK (Foreign Key Actions)

هنگام تعریف Foreign Key، باید مشخص كنیم اگر سطر مادر (Parent) حذف یا به‌روزرسانی شد، با سطرهاي فرزند (Child) چه كنیم. SQL استاندارد چهار گزینه دارد:

عملیاتمعنيكاربرد معمول
CASCADEحذف/تغییر در فرزند هم اعمال شودموجودیت ضعیف (FamilyMember حذف وقتی Employee حذف)
SET NULLمقدار FK در فرزند NULL شودارتباط اختیاري (Employee.ManagerID وقتی Manager حذف)
SET DEFAULTمقدار FK به مقدار پیش‌فرض برگرددكم‌كاربرد
RESTRICT / NO ACTIONاگر فرزند وجود دارد، اجازه حذف/تغییر مادر داده نشودپیش‌فرض؛ ارتباط الزامي
-- مثال: حالت‌هاي مختلف FK Action

-- 1) موجودیت ضعیف → CASCADE
CREATE TABLE OrderItem (
    OrderID INT,
    ItemNo INT,
    PRIMARY KEY (OrderID, ItemNo),
    FOREIGN KEY (OrderID) REFERENCES Orders(OrderID)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- 2) ارتباط اختیاري → SET NULL
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    ManagerID INT NULL,
    FOREIGN KEY (ManagerID) REFERENCES Employee(EmpID)
        ON DELETE SET NULL
);

-- 3) ارتباط الزامي → RESTRICT (پیش‌فرض)
CREATE TABLE Course (
    CourseID INT PRIMARY KEY,
    DepartmentID INT NOT NULL,
    FOREIGN KEY (DepartmentID) REFERENCES Department(DepartmentID)
        ON DELETE RESTRICT
);

نكته: ON DELETE و ON UPDATE مي‌توانند گزینه‌هاي مختلف داشته باشند. اگر مشخص نكنید، پیش‌فرض معمولاً NO ACTION است.

🔷 حالت 2: نگاشت ارتباط M:N (Many-to-Many)

قاعده

ارتباط M:N → حتماً 3 رابطه! 

E1 ──M:N── E2
→ 3 جدول:
  1. E1
  2. E2
  3. E1_E2 (جدول ارتباط)

تصمیم‌گیری: 

✅ تعداد رابطه: 3 (دو موجودیت + یک ارتباط)
✅ PK جدول ارتباط: ترکیب دو FK
✅ صفات ارتباط: در جدول ارتباط

مثال 1: دانشگاه - Student و Course

نمودار ER: 

erDiagram
    STUDENT ||--o{ ENROLLMENT : enrolls
    COURSE ||--o{ ENROLLMENT : "enrolled in"
    
    STUDENT {
        int StudentID PK
        string Name
        string Major
    }
    
    COURSE {
        int CourseID PK
        string CourseName
        int Credits
    }
    
    ENROLLMENT {
        int StudentID FK
        int CourseID FK
        string Semester
        decimal Grade
    }

نگاشت: 

-- رابطه 1: Student (موجودیت قوی)
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Major NVARCHAR(30)
);

-- رابطه 2: Course (موجودیت قوی)
CREATE TABLE Course (
    CourseID INT PRIMARY KEY,
    CourseName NVARCHAR(100),
    Credits INT
);

-- رابطه 3: Enrollment (ارتباط M:N)
CREATE TABLE Enrollment (
    StudentID INT,
    CourseID INT,
    Semester NVARCHAR(10),
    Grade DECIMAL(4,2),
    PRIMARY KEY (StudentID, CourseID, Semester),
    FOREIGN KEY (StudentID) REFERENCES Student(StudentID),
    FOREIGN KEY (CourseID) REFERENCES Course(CourseID)
);

-- نماد:
Student(StudentID, Name, Major)
        ----------

Course(CourseID, CourseName, Credits)
       ---------

Enrollment(StudentID, CourseID, Semester, Grade)
           -------------------------
           ↓ PK (کلید ترکیبی)
           
           StudentID → FK به Student
           ......
           
           CourseID → FK به Course
           ......

داده نمونه: 

Student:
+-----+--------+-------+
|  ID | Name   | Major |
+-----+--------+-------+
| 100 | Ali    | CS    |
| 110 | Sara   | Math  |
+-----+--------+-------+

Course:
+-----+----------+--------+
|  ID | Name     | Credit |
+-----+----------+--------+
| 201 | Database | 3      |
| 202 | Calculus | 4      |
+-----+----------+--------+

Enrollment:
+-----+-----+----------+-------+
| SID | CID | Semester | Grade |
+-----+-----+----------+-------+
| 100 | 201 | Fall2024 | 18.0  |
| 100 | 202 | Fall2024 | 17.0  |

چرا Semester جزو PK؟ → چون یک دانشجو می‌تونه یک درس رو در چند ترم بگیره!

🔷 حالت 3: نگاشت ارتباط 1:N (One-to-Many)

قاعده

ارتباط 1:N → 2 رابطه (بدون جدول ارتباط!) 

E1 ──1:N── E2
→ 2 جدول:
  1. E1 (طرف 1)
  2. E2 (طرف N) + FK به E1

تصمیم‌گیری: 

✅ تعداد رابطه: 2
✅ طرف N کلید خارجی می‌گیره
✅ صفات ارتباط: در طرف N

مثال 1: دانشگاه - Department و Employee

نمودار ER: 

1              N
   Dept ──کار─── Employee
         (From)
erDiagram
    DEPARTMENT ||--o{ EMPLOYEE : employs
    
    DEPARTMENT {
        int DeptID PK
        string DeptName
        string Location
    }
    
    EMPLOYEE {
        int EmpID PK
        string Name
        int Age
        int DeptID FK
        date HireDate
    }

نگاشت: 

-- رابطه 1: Department (طرف 1)
CREATE TABLE Department (
    DeptID INT PRIMARY KEY,
    DeptName NVARCHAR(50),
    Location NVARCHAR(30)
);

-- رابطه 2: Employee (طرف N)
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Age INT,
    DeptID INT,  -- کلید خارجی! ✅
    HireDate DATE,  -- صفت ارتباط!
    FOREIGN KEY (DeptID) REFERENCES Department(DeptID)
);

-- نماد:
Department(DeptID, DeptName, Location)
           -------

Employee(EmpID, Name, Age, DeptID, HireDate)
         ------              ......
                               ↓ FK

تصمیم‌گیری: کی جدول ارتباط نمی‌سازیم؟

سؤال: چرا در 1:N جدول ارتباط نمی‌سازیم؟

جواب:

❌ اگر جدول ارتباط بسازیم:

Dept(DeptID, ...) Employee(EmpID, ...) DeptEmployee(DeptID, EmpID, From) ← لازم نیست!

مشکلات:

  1. هر Employee فقط یک DeptID داره → FK کافیه
  2. جدول DeptEmployee افزونگی ایجاد می‌کنه
  3. JOIN اضافی برای Query‌ها

✅ راه‌حل بهینه:

Dept(DeptID, ...) Employee(EmpID, ..., DeptID, From) ← FK مستقیم!

مزایا:

  1. کمتر جدول
  2. Query سریع‌تر
  3. بدون افزونگی

نکات مهم حالت 3 (1:N)

✅ نکته 1: 1:N فقط 2 جدول (بدون جدول ارتباط!)

✅ نکته 2: طرف N کلید خارجی می‌گیره (نه طرف 1!)

✅ نکته 3: صفات ارتباط در طرف N

✅ نکته 4: FK می‌تونه Null باشه یا نباشه:

  • اگر مشارکت الزامی → NOT NULL
  • اگر مشارکت اختیاری → NULL OK

✅ نکته 5: Index روی FK خوبه برای Performance

❌ خطای رایج: ساختن جدول ارتباط اضافی!

🔷 حالت 4: ارتباط بازگشتی M:N

قاعده

یک موجودیت با خودش ارتباط M:N → 2 رابطه 

E ──M:N── E
→ 2 جدول:
  1. E
  2. E_E (جدول ارتباط)

نکته مهم: باید Rename کنیم!

مثال 1: سیستم دانشگاه - درس و پیش‌نیاز

نمودار ER: 

M              N
   Course ──پیش‌نیاز── Course
erDiagram
    COURSE ||--o{ PREREQUISITE : "has prerequisite"
    COURSE ||--o{ PREREQUISITE : "is prerequisite of"
    
    COURSE {
        int CourseID PK
        string CourseName
        int Credits
    }
    
    PREREQUISITE {
        int CourseID FK
        int PrereqID FK
    }

نگاشت: 

-- رابطه 1: Course
CREATE TABLE Course (
    CourseID INT PRIMARY KEY,
    CourseName NVARCHAR(100),
    Credits INT
);

-- رابطه 2: Prerequisite (ارتباط بازگشتی)
CREATE TABLE Prerequisite (
    CourseID INT,  -- درسی که پیش‌نیاز می‌خواد
    PrereqID INT,  -- درس پیش‌نیاز (Rename شده!)
    PRIMARY KEY (CourseID, PrereqID),
    FOREIGN KEY (CourseID) REFERENCES Course(CourseID),
    FOREIGN KEY (PrereqID) REFERENCES Course(CourseID)
);

-- نماد:
Course(CourseID, CourseName, Credits)
       ---------

Prerequisite(CourseID, PrereqID)
             -------------------
             ↓ PK
             
             CourseID → FK
             ........
             
             PrereqID → FK (Rename!)
             ........

  مثلاً: DataStruct پیش‌نیاز {Database, Algorithm, InfoRetrieval}

→ M:N ✅

Query‌های مفید: 

-- پیش‌نیازهای یک درس
SELECT C2.CourseName AS Prerequisite
FROM Prerequisite P
JOIN Course C2 ON P.PrereqID = C2.CourseID
WHERE P.CourseID = 10;  -- پیش‌نیازهای Database

-- درس‌هایی که DataStruct پیش‌نیازشونه
SELECT C1.CourseName AS Course
FROM Prerequisite P
JOIN Course C1 ON P.CourseID = C1.CourseID
WHERE P.PrereqID = 12;  -- درس‌هایی که DataStruct پیش‌نیازشونه
