1️⃣ دامنه (Domain)

تعریف: دامنه مقادیر یک صفت، مجموعه مقادیر مجاز برای یک صفت را مشخص می‌نماید.

دامنه = مجموعه مقادیر ممکن

مثال: → Age: D_Age = {0, 1, 2, ..., 120} → Gender: D_Gender = {'M', 'F'} → Grade: D_Grade = {0.0, 0.25, 0.5, ..., 20.0} → City: D_City = {'Tehran', 'Isfahan', 'Shiraz', ...}

نکته مهم: هر صفت حتماً باید:

  • نام داشته باشد ✅
  • معنا داشته باشد ✅
  • دامنه مقادیر داشته باشد ✅

2️⃣ صفت (Attribute)

تعریف: صفت یک ویژگی از موجودیت است که دامنه مقادیر مشخص دارد.

مثال - جدول Student: 

+------------+----------+-------------+
| Attribute  | Domain   | Example     |
+------------+----------+-------------+
| StudentID  | Integer  | 100, 110    |
| Name       | String   | 'Ali'       |
| Age        | Integer  | 20, 21, 22  |
| GPA        | Decimal  | 15.5, 18.0  |
| City       | String   | 'Tehran'    |
+------------+----------+-------------+

3️⃣ مجموعه هدینگ (Heading Set)

تعریف: مجموعه هدینگ H یک رابطه R، مجموعه صفات آن رابطه است.

فرمول: 

R(A₁, A₂, A₃, ..., Aₙ)

H = {A₁, A₂, A₃, ..., Aₙ}

مثال: 

-- رابطه Student
Student(StudentID, Name, Major, GPA)

-- مجموعه هدینگ
H_Student = {StudentID, Name, Major, GPA}

-- تعداد صفات (Degree)
|H| = 4

نکته: H یک مجموعه است، پس:

  • ✅ ترتیب مهم نیست
  • ✅ تکرار نداریم
  • ✅ هر صفت یکتاست
این دو یکسان‌اند:
H₁ = {StudentID, Name, Major}
H₂ = {Name, StudentID, Major}

چون مجموعه‌اند! ✅

4️⃣ تاپل (Tuple)

تعریف: تاپل یک سطر از جدول است که مقادیر مشخصی برای هر صفت دارد. 

graph LR
    A[Tuple t]
    
    B[StudentID: 100]

    A --> B

نماد ریاضی: 

t = <v₁, v₂, v₃, ..., vₙ>

که:
vᵢ ∈ Dᵢ  (هر مقدار از دامنه مربوطه)

مثال: 

t₁ = <100, 'Ali', 'CS', 17.5>
t₂ = <110, 'Sara', 'Math', 18.0>
t₃ = <120, 'Reza', 'Physics', 16.5>

هر t یک تاپل است ✅

دسترسی به مقادیر تاپل: 

t[StudentID] = 100
t[Name] = 'Ali'
t[Major] = 'CS'

یا:
t.StudentID = 100
t.Name = 'Ali'

5️⃣ رابطه (Relation)

تعریف نهایی: رابطه R روی مجموعه هدینگ H، یک زیرمجموعه از ضرب دکارتی دامنه‌های صفات است.

فرمول ریاضی: 

R ⊆ D₁ × D₂ × D₃ × ... × Dₙ

که:
Dᵢ = دامنه صفت Aᵢ

به زبان ساده: 

رابطه = مجموعه‌ای از تاپل‌ها

R = {t₁, t₂, t₃, ..., tₘ}

که هر tᵢ یک سطر است ✅

مثال کامل: 

-- رابطه Student
Student(StudentID, Name, Major)

-- دامنه‌ها
D_ID = {100, 110, 120, ...}
D_Name = {'Ali', 'Sara', 'Reza', ...}
D_Major = {'CS', 'Math', 'Physics', ...}

-- ضرب دکارتی (همه حالت‌های ممکن)
D_ID × D_Name × D_Major = همه ترکیبات ممکن

-- رابطه Student (زیرمجموعه‌ای از ضرب دکارتی)
Student = {
  <100, 'Ali', 'CS'>,
  <110, 'Sara', 'Math'>,
  <120, 'Reza', 'Physics'>
}

نکته مهم: چرا زیرمجموعه؟ 

ضرب دکارتی:
→ همه ترکیبات ممکن (حتی بی‌معنی!)
→ مثلاً: <100, 'Ali', 'Math'> + <100, 'Sara', 'CS'> ممکنه!

رابطه واقعی:
→ فقط ترکیبات معتبر (با معنا!)
→ مثلاً: فقط یک دانشجوی Ali با ID=100 داریم ✅

نمایش بصری ضرب دکارتی و رابطه

رابطه واقعی زیرمجموعه‌ای کوچک از فضای بسیار بزرگ ضرب دکارتی است:

خاصیت 1: نام‌دار بودن

تعریف: هر رابطه معرفی شده به سیستم به وسیله یک اسم. 

CREATE TABLE Student (...);  -- Student = نام رابطه
CREATE TABLE Course (...);   -- Course = نام رابطه

نکته: البته می‌توان رابطه داشت که نام ندارد (رابطه بی‌نام یا anonymous) 

-- رابطه بی‌نام (نتیجه Query)
SELECT * FROM Student WHERE GPA > 15;
-- نتیجه یک رابطه است ولی نامی ندارد

خاصیت 2: رابطه یک مجموعه است

چون R مجموعه است:

✅ ترتیب تاپل‌ها مهم نیست:
R₁ = {t₁, t₂, t₃}
R₂ = {t₃, t₁, t₂}
→ R₁ = R₂  (یکسان!)

✅ تکرار نداریم:
R = {t₁, t₁, t₂}  ❌ اشتباه!
R = {t₁, t₂}  ✅ درست!

در عمل: 

-- این دو Query یکسان‌اند:
SELECT * FROM Student;  -- ترتیب تصادفی
SELECT * FROM Student ORDER BY StudentID;  -- ترتیب مشخص

-- ولی همان داده‌ها! ✅

خاصیت 3: هر تاپل یکتاست

اصل: دو تاپل یکسان نمی‌توانیم داشته باشیم! 

❌ اشتباه:
Student = {
  <100, 'Ali', 'CS'>,
  <100, 'Ali', 'CS'>  ← تکراری!
}

✅ درست:
Student = {
  <100, 'Ali', 'CS'>,
  <110, 'Sara', 'Math'>  ← یکتا!
}

چطور تضمین می‌کنیم؟ → با کلید اصلی (Primary Key)! 🔑 

CREATE TABLE Student (
    StudentID INT PRIMARY KEY,  -- تضمین یکتایی!
    Name VARCHAR(50),
    Major VARCHAR(30)
);

-- حالا نمی‌شه دو StudentID یکسان داشت ✅

خاصیت 4: صفات اتمی (Atomic)

تعریف: صفت ساده صفتی است که تجزیه‌ناپذیر باشد. اجزایش در محیط معنی نداشته باشد. 

✅ اتمی (Atomic):
→ Age = 25  (تجزیه‌ناپذیر!)
→ City = 'Tehran'  (تجزیه‌ناپذیر!)

❌ غیراتمی (Non-Atomic):
→ FullName = 'Ali Rezaei'  (تجزیه‌پذیر: Ali + Rezaei)
→ Address = 'Tehran, Valiasr, No.10'  (تجزیه‌پذیر!)

مثال اصلاح: 

-- ❌ غلط
CREATE TABLE Student (
    FullName VARCHAR(100)  -- تجزیه‌پذیر!
);

-- ✅ درست
CREATE TABLE Student (
    FirstName VARCHAR(50),  -- اتمی ✅
    LastName VARCHAR(50)    -- اتمی ✅
);

خاصیت 5: درجه رابطه (Degree)

تعریف: درجه رابطه n برابر است با تعداد صفات آن رابطه. 

Degree(R) = |H| = n

مثال: 

-- رابطه Student
Student(StudentID, Name, Major, GPA)

-- درجه
Degree(Student) = 4  (4 صفت)

انواع رابطه بر اساس درجه:

Degreeناممثال
1UnaryR(A)
2BinaryR(A, B)
3TernaryR(A, B, C)
nn-aryR(A₁, A₂, ..., Aₙ)
#### خاصیت 6: کاردینالیتی (Cardinality)

تعریف: کاردینالیتی رابطه R برابر است با تعداد تاپل‌های آن. 

Cardinality(R) = |R| = m

مثال: 

Student = {
  <100, 'Ali', 'CS'>,
  <110, 'Sara', 'Math'>,
  <120, 'Reza', 'Physics'>
}

Cardinality(Student) = 3  (3 تاپل)

نکته: کاردینالیتی متغیر است! 

امروز: Cardinality(Student) = 100
فردا (بعد از ثبت‌نام): Cardinality(Student) = 150

ولی Degree ثابت است! ✅

🔢 درجه رابطه و تعداد دامنه‌ها

قاعده مهم: اگر رابطه R دارای n صفت باشد: 

حداکثر تعداد دامنه‌ها = n
حداقل تعداد دامنه‌ها = 1

چرا؟ 

حالت 1: هر صفت دامنه جداگانه (بیشترین حالت)
→ n صفت → n دامنه

Student(ID, Name, Age)
→ D_ID, D_Name, D_Age  (3 دامنه)

حالت 2: همه صفات یک دامنه (کمترین حالت)
→ n صفت → 1 دامنه

Points(X, Y, Z)
→ همه از D_Real  (1 دامنه: اعداد حقیقی)

فرمول دقیق: 

اگر درجه رابطه = n
→ تعداد دامنه‌ها: 1 ≤ d ≤ n

📝 مثال جامع - سیستم دانشگاه

-- رابطه 1: Student
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    FirstName VARCHAR(50),
    LastName VARCHAR(50),
    Major VARCHAR(30),
    GPA DECIMAL(4,2)
);

-- رابطه 2: Course
CREATE TABLE Course (
    CourseID INT PRIMARY KEY,
    CourseName VARCHAR(100),
    Credits INT,
    DeptName VARCHAR(50)
);

-- رابطه 3: Enrollment
CREATE TABLE Enrollment (
    StudentID INT,
    CourseID INT,
    Semester VARCHAR(10),
    Grade DECIMAL(4,2),
    PRIMARY KEY (StudentID, CourseID, Semester)
);

تحلیل:

Student:

  • Heading: H = {StudentID, FirstName, LastName, Major, GPA}
  • Degree: 5
  • Cardinality: فرض کنیم 1000 دانشجو
  • دامنه‌ها: D_ID (Integer), D_Name (String), D_Major (String), D_GPA (Decimal)

Course:

  • Degree: 4
  • Cardinality: فرض کنیم 200 درس

Enrollment:

  • Degree: 4
  • Cardinality: فرض کنیم 5000 ثبت‌نام
  • کلید اصلی: ترکیبی (Composite Key)

✍️ تمرینات بخش ۴.۱

تمرین 1 (تشریحی):

رابطه Employee با صفات زیر داریم: 

Employee(EmpID, FullName, DeptCode, Salary, HireDate)

سوالات:

  • الف) مجموعه هدینگ H را بنویسید.
  • ب) درجه رابطه چند است؟
  • ج) دامنه مناسب برای هر صفت تعریف کنید.
  • د) یک تاپل نمونه بنویسید.
  • ه) آیا FullName صفت اتمی است؟ چرا؟

تمرین 2 (تستی):

کدام گزینه نادرست است؟ 

الف) رابطه یک مجموعه است، پس ترتیب تاپل‌ها مهم نیست.
ب) هر رابطه حداقل یک کلید اصلی دارد.
ج) درجه رابطه با اضافه شدن تاپل جدید تغییر می‌کند.
د) کاردینالیتی رابطه متغیر است.

تمرین 3 (تحلیلی):

رابطه Product: 

CREATE TABLE Product (
    ProductID INT,
    ProductName VARCHAR(100),
    Price DECIMAL(10,2),
    Category VARCHAR(50)
);

-- داده نمونه
INSERT INTO Product VALUES

(2, 'Mouse', 150000, 'Electronics'),

سوالات:

  • الف) چند تاپل داریم؟
  • ب) درجه چند است؟
  • ج) آیا این رابطه کلید اصلی دارد؟ اگر نه، چرا مشکل است؟
  • د) اگر دو محصول با همان نام و قیمت داشته باشیم چه اتفاقی می‌افتد؟

تمرین 4 (طراحی):

سیستم کتابخانه: 

موجودیت‌ها: Book, Member, Borrow

Book: شناسه کتاب، عنوان، نویسنده، سال انتشار
Member: شناسه عضو، نام، شماره تماس
Borrow: شناسه قرض، شناسه کتاب، شناسه عضو، تاریخ قرض، تاریخ برگشت

طراحی کنید:

  • رابطه‌ها را با صفات کامل بنویسید
  • برای هر رابطه: Heading, Degree, دامنه‌ها
  • یک تاپل نمونه برای هر رابطه

تمرین 5 (مفهومی):

سؤال: چرا می‌گوییم رابطه زیرمجموعه ضرب دکارتی است و نه برابر؟

با مثال کامل توضیح دهید و نشان دهید که چطور ضرب دکارتی شامل ترکیبات بی‌معنی هم می‌شود.

تمرین 6 (پیشرفته):

رابطه زیر را در نظر بگیرید: 

CREATE TABLE Employee (

    Phone VARCHAR(20),  -- چند شماره تلفن!

(100, 'Ali', '09121234567, 02188776655', 'Java, Python, SQL')

مشکلات:

  • الف) کدام خاصیت رابطه نقض شده؟
  • ب) چرا این طراحی مشکل‌ساز است؟
  • ج) راه‌حل چیست؟ رابطه را اصلاح کنید.
