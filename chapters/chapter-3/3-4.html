🎯 مقدمه تعاملی

خوب دانشجوی عزیز، حالا یکی از مهم‌ترین مزایای معماری سه‌لایه رو یاد می‌گیریم! 🔓

فرض کن یک برنامه نوشتیم که با پایگاه داده کار می‌کنه: 

# برنامه پایتون
def get_employees():
    query = "SELECT EmpID, Name, Salary FROM Employee"
    return execute_query(query)

مشکل:
❓ اگر ایندکس اضافه کنیم چی می‌شه؟
❓ اگر فایل رو تغییر بدیم چی می‌شه؟
❓ اگر ستون جدید اضافه کنیم چی می‌شه؟
❓ اگر جدول رو Split کنیم چی می‌شه؟

→ باید برنامه رو تغییر بدیم؟ ❌
→ یا برنامه خودکار کار می‌کنه؟ ✅

جواب: استقلال داده‌ای (Data Independence)! ✨

📖 تعریف استقلال داده‌ای

مفهوم استقلال داده‌ای: برنامه کاربردی با Data در ارتباط است. اگر ساختار جداول عوض شود نباید برنامه کاربردی تحت تأثیر قرار بگیرد. اگر هر چیزی در Database عوض شود برنامه نباید تحت تأثیر قرار بگیرد.

جنبه‌های قابل تغییر

در نوع PDI چه جنبه‌هایی از سطح فیزیکی می‌تواند تغییر یابد؟

✅ 7 جنبه قابل تغییر:

  1. نوع فیلدها (Type)
  • INT → BIGINT
  • VARCHAR(50) → VARCHAR(100)
  1. فرمت رکوردها (Format)
  • Fixed → Variable
  • Compressed → Uncompressed
  1. طول رکوردها (Length)
  • 100 byte → 200 byte
  1. ساختار فایل‌ها (File Structure)
  • Heap → B+Tree
  • Unordered → Ordered
  1. استراتژی دستیابی (Access Strategy)
  • Sequential → Indexed
  • Hash → B+Tree
  1. ارتباط منطقی بین فایل‌ها
  • 1 Table → 1 File
  • 1 Table → 2 Files
  1. رسانه ذخیره‌سازی (Storage Media)
  • Disk 1 → Disk 2
  • HDD → SSD

مثال‌های عملی PDI

مثال 1: اضافه کردن ایندکس 

-- قبل: بدون ایندکس
SELECT * FROM Employee WHERE Salary > 50000000;
-- → Full Table Scan (کند!)

-- اضافه کردن ایندکس
CREATE INDEX idx_salary ON Employee(Salary);
-- → Indexed Scan (سریع!)

-- برنامه تغییر نمی‌کنه! ✅
-- همان Query، ولی سریع‌تر! ✅

مثال 2: تغییر ساختار فایل 

قبل: Heap File (نامرتب)
→ Employee.dat (Unordered)

بعد: B+Tree File (مرتب)
→ Employee_indexed.dat (Ordered on EmpID)

برنامه تغییر نمی‌کنه! ✅
همان SELECT، ولی سریع‌تر! ✅

مثال 3: انتقال به دیسک دیگر 

قبل: /disk1/data/employee.dat
بعد: /disk2/data/employee.dat

برنامه:
SELECT * FROM Employee;

→ همچنان کار می‌کنه! ✅
→ تغییر path لازم نیست! ✅

مثال 4: تغییر نگاشت Table→File 

قبل:
Employee Table → 1 File

بعد:
Employee Table → 2 Files
  - employee_current.dat (سال جاری)
  - employee_archive.dat (آرشیو)

برنامه:
SELECT * FROM Employee WHERE Year = 2024;

→ DBMS خودش مدیریت می‌کنه! ✅
→ برنامه تغییر نمی‌کنه! ✅

چرا PDI تأثیر نمی‌گذارد؟

چرا مواردی در سطح برنامه‌های کاربردی تأثیر نمی‌گذارد:

✅ دو دلیل:

  1. برنامه‌ها در سطح خارجی کار می‌کنن:
  • برنامه با View کار می‌کنه
  • View فرا فایلی است
  • جنبه‌های فایلینگ نداره
  1. سطح ادراکی واسط است:
  • بین خارجی و داخلی
  • نگاشت C/I تغییرات رو جذب می‌کنه
  • برنامه محافظت می‌شه

دلایل تغییرات منطقی

دلایلی که باعث تغییرات در سطح ادراکی می‌شوند:

✅ 4 دسته کلی:

  1. رشد دیتابیس:
  • افزایش داده
  • نیاز به بهینه‌سازی
  1. سازماندهی مجدد:
  • Reorganization
  • بهبود ساختار
  1. نیازهای جدید:
  • صفت جدید (ستون)
  • ارتباط جدید
  • موجودیت جدید
  1. بهینه‌سازی:
  • نرمال‌سازی
  • De-normalization

دلیل 1: ایجاد فایلینگ کارآتر

مشکل:
→ جدول Employee (1,000,000 رکورد)
→ 20 ستون، بعضی کم‌استفاده
→ Query‌ها روی 5 ستون اول خیلی زیاده
→ I/O زیاد، کندی!

راه‌حل: Split
→ Emp_Frequent (5 ستون پرکاربرد)
→ Emp_Details (15 ستون کم‌استفاده)

نتیجه:
→ Query‌ها سریع‌تر ✅
→ I/O کمتر ✅
→ فایلینگ کارآتر ✅

مثال: 

-- قبل: یک جدول بزرگ
Employee (EmpID, Name, Dept, Salary, Phone, Email, 
          Address, City, Country, ZipCode, ...) -- 20 ستون

-- 90% Query‌ها:
SELECT EmpID, Name, Dept, Salary FROM Employee;
-- → باید 20 ستون رو بخونه! ❌

-- بعد: Split
Emp_Main (EmpID, Name, Dept, Salary)  -- پرکاربرد
Emp_Contact (EmpID, Phone, Email, Address, ...)  -- کم‌استفاده

-- حالا:
SELECT EmpID, Name, Dept, Salary FROM Emp_Main;
-- → فقط 4 ستون رو می‌خونه! ✅

دلیل 2: نرمال‌تر سازی رابطه‌های موجود

مشکل: جداول دارای آنومالی

مثال:
Student_Course (StudentID, Name, CourseID, CourseName, Grade)
→ افزونگی: Name و CourseName تکرار می‌شن ❌
→ آنومالی Update: تغییر CourseName همه‌جا ❌
→ آنومالی Delete: حذف آخرین دانشجو → حذف درس ❌

راه‌حل: نرمال‌سازی (3NF)
→ Student (StudentID, Name)
→ Course (CourseID, CourseName)
→ Enrollment (StudentID, CourseID, Grade)

نتیجه:
→ هیچ افزونگی ✅
→ هیچ آنومالی ✅

دلیل 3: توزیع در سایت‌های مختلف (DDB)

مشکل: یک شرکت با 3 شعبه

Employee (EmpID, Name, Branch, Salary, ...)
→ همه داده‌ها در یک سایت (مرکزی)
→ شعبه تهران باید به مرکز متصل بشه
→ شعبه اصفهان باید به مرکز متصل بشه
→ Network traffic زیاد ❌

راه‌حل: Split بر اساس Branch
→ Emp_Tehran در سایت تهران
→ Emp_Isfahan در سایت اصفهان
→ Emp_Shiraz در سایت شیراز

نتیجه:
→ هر شعبه داده‌های خودش رو داره ✅
→ دسترسی محلی (Local Access) ✅
→ Network traffic کمتر ✅
→ View کلی برای سازگاری ✅

مثال: 

-- قبل: یک جدول مرکزی
Employee (EmpID, Name, Branch, Salary)
-- در Server مرکزی

-- بعد: Split جغرافیایی
-- Site Tehran:
CREATE TABLE Emp_Tehran AS
SELECT * FROM Employee WHERE Branch = 'Tehran';

-- Site Isfahan:
CREATE TABLE Emp_Isfahan AS
SELECT * FROM Employee WHERE Branch = 'Isfahan';

-- View کلی (در مرکز):
CREATE VIEW Employee AS
SELECT * FROM Emp_Tehran
UNION ALL
SELECT * FROM Emp_Isfahan
UNION ALL
SELECT * FROM Emp_Shiraz;

دلیل 4: کاهش Granularity Lock و افزایش همروندی

مشکل: Table-Level Lock

Scenario:
→ User1: UPDATE Employee SET Salary = ... WHERE EmpID = 100
→ User2: UPDATE Employee SET Salary = ... WHERE EmpID = 200
→ با Table-Lock: User2 باید صبر کنه! ❌
→ همروندی پایین ❌

راه‌حل: Split + Row-Level Lock
→ Emp_Dept1 (100 رکورد)
→ Emp_Dept2 (100 رکورد)
→ Lock کوچک‌تر
→ همروندی بالاتر ✅

یا با Row-Level Lock:
→ User1 روی Row 100 Lock
→ User2 روی Row 200 Lock
→ همزمان کار می‌کنن! ✅

Granularity Lock: 

Lock Levels:
┌─────────────────┐
│ Database Lock   │ (خیلی درشت - همروندی صفر)
├─────────────────┤
│ Table Lock      │ (درشت - همروندی پایین)
├─────────────────┤
│ Page Lock       │ (متوسط)
├─────────────────┤
│ Row Lock        │ (ریز - همروندی بالا) ✅
└─────────────────┘

با Split جدول:
→ Lock‌ها کوچک‌تر می‌شن
→ Conflict کمتر
→ همروندی بیشتر

دلیل 5: محدودیت DBMS از نظر حداکثر ستون

مشکل: محدودیت تعداد ستون

مثال:
→ SQL Server: حداکثر 1024 ستون
→ MySQL: حداکثر 4096 ستون (با محدودیت سایز)
→ Oracle: حداکثر 1000 ستون

Scenario:
→ Patient جدول بیمارستان
→ 500 ستون: اطلاعات پایه، تاریخچه، آزمایش، ...
→ می‌خوایم 600 ستون اضافه کنیم
→ DBMS اجازه نمی‌ده! ❌

راه‌حل: Split اجباری
→ Patient_Basic (200 ستون)
→ Patient_Medical (200 ستون)
→ Patient_Lab (200 ستون)
→ View: Patient (همه رو JOIN می‌کنه)

نتیجه:
→ محدودیت رعایت شده ✅
→ همه داده‌ها ذخیره شده ✅

مثال واقعی: 

-- ❌ خطا!
CREATE TABLE HugeTable (
    Col1 INT,
    Col2 INT,
    ...
    Col1025 INT  -- خطا: بیشتر از 1024!
);
-- ERROR: Too many columns

-- ✅ راه‌حل:
CREATE TABLE HugeTable_Part1 (Col1...Col512);
CREATE TABLE HugeTable_Part2 (Col513...Col1024);

CREATE VIEW HugeTable AS
SELECT T1.*, T2.*
FROM HugeTable_Part1 T1
JOIN HugeTable_Part2 T2 ON T1.ID = T2.ID;

مثال 1: اضافه کردن ستون 

-- جدول قبل
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Salary DECIMAL(12,2)
);

-- View برنامه
CREATE VIEW EmpView AS
SELECT EmpID, Name
FROM Employee;

-- برنامه
SELECT * FROM EmpView;  -- فقط EmpID, Name

-- تغییر: اضافه کردن Email
ALTER TABLE Employee ADD Email NVARCHAR(100);

-- برنامه همچنان کار می‌کنه! ✅
SELECT * FROM EmpView;  -- همچنان EmpID, Name

مثال 2: Split جدول (تقسیم) 

-- قبل: یک جدول
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Major NVARCHAR(30),
    GPA DECIMAL(3,2),
    Phone NVARCHAR(20),
    Address NVARCHAR(100)
);

-- بعد: دو جدول
CREATE TABLE Student_Personal (
    StudentID INT PRIMARY KEY,
    Name NVARCHAR(50),
    Major NVARCHAR(30),
    GPA DECIMAL(3,2)
);

CREATE TABLE Student_Contact (
    StudentID INT PRIMARY KEY,
    Phone NVARCHAR(20),
    Address NVARCHAR(100)
);

-- ایجاد View برای سازگاری
CREATE VIEW Student AS
SELECT 
    P.StudentID,
    P.Name,
    P.Major,
    P.GPA,
    C.Phone,
    C.Address
FROM Student_Personal P
JOIN Student_Contact C ON P.StudentID = C.StudentID;

-- برنامه تغییر نمی‌کنه! ✅
SELECT * FROM Student;  -- همچنان کار می‌کنه!

مثال Split: 

-- جدول قبل
CREATE TABLE S (
    S# INT PRIMARY KEY,
    SName NVARCHAR(50),
    City NVARCHAR(30),
    Status INT
);

-- Split به دو جدول
CREATE TABLE Sx (
    S# INT PRIMARY KEY,
    SName NVARCHAR(50)
);

CREATE TABLE Sy (
    S# INT PRIMARY KEY,
    City NVARCHAR(30),
    Status INT
);

-- INSERT داده
INSERT INTO Sx(S#, SName)
SELECT S#, SName
FROM S;

INSERT INTO Sy(S#, City, Status)
SELECT S#, City, Status
FROM S;

-- ایجاد View S
CREATE VIEW S AS
SELECT Sx.S#, Sx.SName, Sy.City, Sy.Status
FROM Sx JOIN Sy ON Sx.S# = Sy.S#;

مثال 3: Merge جداول (ادغام) 

-- قبل: دو جدول
CREATE TABLE Current_Employee (...);
CREATE TABLE Archive_Employee (...);

-- بعد: یک جدول
CREATE TABLE All_Employee (
    ...,
    IsArchived BIT
);

-- ایجاد View‌ها برای سازگاری
CREATE VIEW Current_Employee AS
SELECT * FROM All_Employee WHERE IsArchived = 0;

CREATE VIEW Archive_Employee AS
SELECT * FROM All_Employee WHERE IsArchived = 1;

-- برنامه‌ها تغییر نمی‌کنن! ✅

تکنیک تعریف View روی View

: مفهوم دید و مکانیزم دید بر روی دید به این ترتیب که قبل از حذف جدول مبنای S همین جدول را (با همان نام و همان ستون‌ها) به صورت یک View تعریف می‌نماییم. 

-- مراحل:

-- 1. جدول اصلی S داریم
CREATE TABLE S (...);

-- 2. برنامه‌ها با S کار می‌کنن
SELECT * FROM S;

-- 3. می‌خوایم S رو Split کنیم
-- ابتدا S رو به View تبدیل می‌کنیم

CREATE VIEW S AS
SELECT Sx.S#, Sx.SName, Sy.City, Sy.Status
FROM Sx JOIN Sy ON Sx.S# = Sy.S#;

-- 4. حذف جدول اصلی S
DROP TABLE S;

-- 5. برنامه‌ها همچنان کار می‌کنن! ✅
SELECT * FROM S;  -- حالا S یک View است!

نتیجه : در سیستم، پس از حذف جدول مبنای S، کماکان جدولی با نام S وجود دارد. این جدول مجازی می‌باشد. در نتیجه View‌های تعریف شده روی S همچنان معتبر باقی می‌مانند.

هزینه: 

✅ مزیت:
- LDI در عملیات بازیابی 100% تأمین است

❌ معایب:
- یک Overhead ناشی از Mapping E/E
- نگاشت External → External

پیامد 1: نامعتبر شدن View‌ها

نامعتبر شدن دیدهایی که قبلاً روی آن جدول تعریف شده‌اند و عدم اجرای برنامه‌هایی که از این دیدها استفاده می‌نمایند.

    S# INT,
    SName NVARCHAR(50),
    City NVARCHAR(30),
    Status INT
);

-- View روی S
CREATE VIEW ActiveSuppliers AS

FROM S
WHERE Status > 100;

-- برنامه استفاده می‌کنه
SELECT * FROM ActiveSuppliers;  -- ✅ کار می‌کنه

-- حذف S
DROP TABLE S;  -- ❌

-- حالا View خراب شده!
SELECT * FROM ActiveSuppliers;  -- ❌ ERROR!
-- "Table 'S' doesn't exist"

پیامد 2: نامعتبر شدن Index‌ها

Index‌هایی که برای این جدول تعریف شده‌اند، نامعتبر می‌شوند. مگر اینکه تدبیری برای این کار اندیشیده شود. 

-- Index روی S
CREATE INDEX idx_city ON S(City);
CREATE INDEX idx_status ON S(Status);

-- حذف S
DROP TABLE S;

-- Index‌ها هم حذف می‌شن! ❌
-- idx_city → GONE ❌
-- idx_status → GONE ❌

پیامد 3: شکستن برنامه‌ها

برنامه‌های کاربردی:
→ با جدول S کار می‌کنن ✅
→ با View‌های روی S کار می‌کنن ✅

حذف S:
→ برنامه‌ها دیگه اجرا نمی‌شن! ❌
→ خطا در زمان اجرا! ❌
→ سیستم از کار می‌افته! ❌

مرحله 5: 🔑 کلید - ایجاد View با نام S (قبل از حذف!) 

-- این مهم‌ترین مرحله است! ⭐
CREATE VIEW S AS
SELECT Sx.S#, Sx.SName, Sy.City, Sy.Status
FROM Sx 
JOIN Sy ON Sx.S# = Sy.S#;

-- حالا S یک View است (نه Table!)

مرحله 6: حذف جدول اصلی S 

-- حالا می‌تونیم بدون مشکل حذف کنیم

-- View ActiveSuppliers همچنان کار می‌کنه!
SELECT * FROM ActiveSuppliers;  -- ✅

-- چون:
-- ActiveSuppliers → S (View) → Sx + Sy (Tables)

کاربرد 1: تأمین استقلال منطقی

تأمین استقلال داده‌ای منطقی در قبال سازماندهی مجدد برای برنامه‌ها با عملیات بازیابی. 

سناریو: سازماندهی مجدد

قبل:
→ Employee (20 ستون)
→ خیلی بزرگ!
→ Query‌ها کند!

بعد:
→ Emp_Personal (10 ستون)
→ Emp_Professional (10 ستون)
→ View: Employee (هر دو رو JOIN می‌کنه)

نتیجه:
→ برنامه‌ها تغییر نمی‌کنن! ✅
→ LDI 100% برای بازیابی! ✅

کاربرد 2: تقویت امنیت

تقویت امنیت پایگاه داده چون کاربران حتی Table‌ها را هم نمی‌بینند. 

قبل:
→ کاربران Table‌ها رو می‌دیدن
→ View فقط محدودکننده بود

بعد (با تکنیک View روی View):
→ Table‌ها حذف شدن!
→ فقط View‌ها وجود دارن!
→ کاربران اصلاً Table نمی‌بینن! ✅

→ لایه امنیتی قوی‌تر! 🔒

مثال: 

-- جداول واقعی (پنهان)
CREATE TABLE Sensitive_Data (...);
CREATE TABLE Audit_Log (...);

-- View‌ها (قابل دسترس)
CREATE VIEW Employee AS ...;
CREATE VIEW Department AS ...;

-- کاربران فقط View می‌بینن!
GRANT SELECT ON Employee TO User1;  -- ✅
-- User1 نمی‌تونه Sensitive_Data ببینه! ✅

بازیابی (SELECT): 100% تأمین ✅

-- تغییر: Split جدول S
-- قبل: Table S
-- بعد: View S (Sx + Sy)

-- Query برنامه
SELECT * FROM S WHERE City = 'Tehran';

-- تبدیل اتوماتیک به:
SELECT Sx.S#, Sx.SName, Sy.City, Sy.Status
FROM Sx JOIN Sy ON Sx.S# = Sy.S#
WHERE Sy.City = 'Tehran';

-- ✅ کار می‌کنه!
-- ✅ LDI 100%
-- ⚠️ Overhead: JOIN اضافی

ذخیره‌سازی: شرطی ⚠️

INSERT: 

-- View S (از Sx + Sy)
CREATE VIEW S AS
SELECT Sx.S#, Sx.SName, Sy.City, Sy.Status
FROM Sx JOIN Sy ON Sx.S# = Sy.S#;

-- تلاش برای INSERT
INSERT INTO S VALUES (100, 'Ali', 'Tehran', 20);

-- ❌ ممکنه کار نکنه!
-- چون:
-- - View از دو جدول است (JOIN)
-- - Updatable نیست!

راه‌حل: Instead Of Trigger 

CREATE TRIGGER trg_insert_s
INSTEAD OF INSERT ON S
FOR EACH ROW
BEGIN
    INSERT INTO Sx(S#, SName) VALUES (NEW.S#, NEW.SName);
    INSERT INTO Sy(S#, City, Status) VALUES (NEW.S#, NEW.City, NEW.Status);
END;

-- حالا INSERT کار می‌کنه! ✅
INSERT INTO S VALUES (100, 'Ali', 'Tehran', 20);

UPDATE: 

-- تلاش برای UPDATE
UPDATE S SET SName = 'Reza' WHERE S# = 100;

-- ممکنه کار کنه یا نکنه! ⚠️
-- بستگی به View داره

-- با Trigger:
CREATE TRIGGER trg_update_s
INSTEAD OF UPDATE ON S
FOR EACH ROW
BEGIN
    UPDATE Sx SET SName = NEW.SName WHERE S# = NEW.S#;
    UPDATE Sy SET City = NEW.City, Status = NEW.Status WHERE S# = NEW.S#;
END;

-- حالا UPDATE کار می‌کنه! ✅

DELETE: 

-- تلاش برای DELETE
DELETE FROM S WHERE S# = 100;

-- با Trigger:
CREATE TRIGGER trg_delete_s
INSTEAD OF DELETE ON S
FOR EACH ROW
BEGIN
    DELETE FROM Sx WHERE S# = OLD.S#;
    DELETE FROM Sy WHERE S# = OLD.S#;
END;

-- حالا DELETE کار می‌کنه! ✅
