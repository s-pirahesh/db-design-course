🎯 مقدمه تعاملی

خوب دانشجوی عزیز، در بخش قبل با معماری متمرکز و کلاینت/سرور آشنا شدیم. حالا می‌خوایم بریم سراغ قدرتمندترین معماری: پایگاه داده توزیع‌شده (DDB)!

فرض کن یک شرکت بین‌المللی داری با دفاتر در:

  • تهران 🇮🇷
  • دبی 🇦🇪
  • لندن 🇬🇧
  • نیویورک 🇺🇸

سوال: یک DB در تهران بذاریم و همه ازش استفاده کنن؟ ❌

مشکلات:

  • تاخیر شبکه برای لندن و نیویورک خیلی زیاده! 🐌
  • اگر شبکه قطع شه، دفاتر خارج نمی‌تونن کار کنن! ❌
  • سرعت خیلی پایینه! 😰

راه حل: پایگاه داده توزیع‌شده! 🎉

📖 تعریف DDB ()

DDB (Distributed Data Base): نوعی معماری پایگاهی می‌باشد که در آن یک دیتابیس مطلقاً مجتمع داریم ولی با داده‌های توزیع شده در سایت‌های مختلف. فیزیکی - نامجتمع و نامتمرکز سه‌گونه‌ای که از منظر کاربر یک سیستم پایگاهی دیده می‌شود.

تحلیل تعریف

mindmap

    از نظر منطقی
      یک DB
      مجتمع
      یکپارچه
    از نظر فیزیکی
      چند سایت
      نامجتمع
      نامتمرکز
    از نظر کاربر
      شفاف
      نمی بینه کجاست
      یک DB می بینه

نکات کلیدی:

  1. منطقی → مجتمع: کاربر یک DB می‌بینه ✅
  2. فیزیکی → نامجتمع: داده‌ها در چند سایت هستن ✅
  3. کاربر → نمی‌دونه: شفافیت کامل ✅

🔍 دو مدل دسترسی در DDB

1. مدل محلی (Local Model)

: "اگر داده‌های مورد نظر کاربر در سایتی باشد که برنامه کاربر در آن اجرا می‌شود. در اصطلاح می‌گویند کاربر با اسلوب محلی یا Local Model به داده‌ها دسترسی پیدا نموده است." 

sequenceDiagram
    participant U as کاربر تهران
    participant DB as DBMS تهران
    participant Data as داده محلی
    
    U->>DB: SELECT * FROM Customers_Iran
    Note over DB: داده محلی است ✅
    DB->>Data: خواندن
    Data->>DB: داده
    DB->>U: نتیجه (سریع! ⚡)

مزیت: خیلی سریعه! چون داده همون‌جاست.

2. مدل راه دور (Remote Model)

: "اما اگر داده‌های مورد نظر کاربر در سایت‌های راه دور باشد از نظر کاربر، برنامه کماکان بصورت محلی اجرا می‌شود. یعنی کاربر اصلا نمی‌بیند که داده‌ها چگونه و در کجا ذخیره شده اند." 

sequenceDiagram
    participant U as کاربر تهران
    participant DB1 as DBMS تهران
    participant N as شبکه
    participant DB2 as DBMS لندن
    participant Data as داده لندن
    
    U->>DB1: SELECT * FROM Customers_Europe
    Note over DB1: داده در لندن است
    DB1->>N: درخواست از لندن
    N->>DB2: درخواست
    DB2->>Data: خواندن
    Data->>DB2: داده
    DB2->>N: پاسخ
    N->>DB1: پاسخ
    DB1->>U: نتیجه (کندتر 🐌 ولی شفاف!)

نکته مهم: کاربر نمی‌دونه داده از لندن اومده! همچنان فکر می‌کنه محلی کار می‌کنه! ✨

🎨 شفافیت (Transparency) - قلب DDB

ایده اصلی: کاربر نباید بفهمه که سیستم توزیع‌شده است!

: "کاربر سایت‌های دیگر را نمی‌بیند از لحاظ تکنیکی می‌گوییم در این معماری از جنبه‌های مختلف شفافیت وجود دارد."

5 نوع شفافیت ()

1. شفافیت مکان (Location Transparency)

: "کاربر محل داده‌ها را نمی‌داند." 

-- کاربر می‌نویسه:
SELECT * FROM Customers WHERE Country = 'Iran';

-- نمی‌دونه که این داده در سایت تهران است!
-- DDBMS خودش می‌فهمه و از اونجا می‌گیره ✅

بدون شفافیت مکان: (بد ❌) 

SELECT * FROM Tehran.DB.Customers WHERE Country = 'Iran';
-- کاربر مجبوره بگه "Tehran"!

2. شفافیت توزیع (Distribution Transparency)

: "کاربر نحوه توزیع را نمی‌داند." 

مثال: جدول Customers توزیع شده:
- Customers_Iran → تهران
- Customers_Europe → لندن  
- Customers_USA → نیویورک

کاربر می‌بینه: یک جدول Customers ✅
نمی‌دونه که 3 تکه است!

3. شفافیت سخت‌افزار (Hardware Transparency)

: "کاربر سخت‌افزار را نمی‌بیند (سخت‌افزار مورد استفاده در سایت‌های دیگر قرار دارد)" 

سایت تهران: سرور HP
سایت لندن: سرور Dell
سایت نیویورک: سرور IBM

کاربر نمی‌دونه! فقط یک DB می‌بینه ✅

4. شفافیت سیستم عامل (OS Transparency)

: "کاربر فقط سیستم عامل خود را می‌بیند." 

سایت تهران: Windows Server
سایت لندن: Linux (Ubuntu)
سایت نیویورک: Unix (Solaris)

کاربر در تهران فقط Windows رو می‌بینه ✅

5. شفافیت شبکه (Network Transparency)

: "کاربر شبکه‌ها را نمی‌بیند." 

بین سایت‌ها:
- Fiber Optic
- Satellite
- VPN
- MPLS

کاربر نمی‌دونه! فقط Query می‌فرسته ✅

  • نمی‌دونه چه شبکه‌ای استفاده شده (Network) ✅

همه چیز شفاف! ✨✨✨

🔧 نکته مهم: استقلال (Independence)

: "گاه به جای شفافیت از Independence یا استقلال استفاده می‌شود." 

شفافیت = استقلال

Location Transparency = Location Independence
Distribution Transparency = Distribution Independence
...

معنا: سیستم مستقل از این جزئیات است!

🏗️ مراحل طراحی DDB ()

فاز 1: طراحی سیستم مانند CDB (پایگاه داده متمرکز) انجام می‌گیرد. 

مرحله 1: طراحی معمولی
↓
- نمودار ER
- جداول
- رابطه‌ها
- کلیدها

→ انگار متمرکز است!

فاز 2: طراحی توزیع بر اساس استراتژی‌های خاص انجام می‌گیرد. 

مرحله 2: طراحی توزیع
↓
سوالات:
- چه داده‌هایی را در چه سایتی ذخیره نماییم؟
- داده‌ها را چگونه توزیع نماییم؟

استراتژی‌ها:
1. بر اساس مکان کاربران
2. بر اساس حجم تراکنش‌ها
3. بر اساس قوانین کسب و کار

مثال طراحی: شرکت بین‌المللی

فاز 1: طراحی متمرکز 

-- جداول:
CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    Name VARCHAR(100),
    Country VARCHAR(50),
    ...
);

CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    CustomerID INT,
    OrderDate DATE,
    ...
);

فاز 2: طراحی توزیع 

استراتژی: توزیع بر اساس Country

سایت تهران:
- Customers WHERE Country IN ('Iran', 'Iraq', 'Afghanistan')
- Orders مربوط به این Customers

سایت لندن:
- Customers WHERE Country IN ('UK', 'France', 'Germany')
- Orders مربوط به این Customers

سایت نیویورک:
- Customers WHERE Country IN ('USA', 'Canada', 'Mexico')
- Orders مربوط به این Customers

🔄 برنامه سراسری (Global Program)

: "منظور از برنامه سراسری برنامه‌ای است که برای اجرا شدن به بیش از یک سایت نیاز داشته باشد." 

graph TB

مثال: 

-- برنامه سراسری: گزارش فروش جهانی
SELECT Country, SUM(Sales)
FROM Orders
GROUP BY Country;

-- این Query نیاز داره:
-- 1. داده از سایت تهران (ایران)
-- 2. داده از سایت لندن (اروپا)
-- 3. داده از سایت نیویورک (آمریکا)

→ برنامه سراسری است! ✅

نکته : "در این معماری هر سایت حداقل در اجرای یک برنامه سراسری مشارکت دارد."

🎯 نرم‌افزار DDB: DDBMS

: "نرم افزار اصلی در این سیستم DDBMS است که یک نوع DBMS است." 

DDBMS = DBMS + قابلیت DF (وظایف توزیع شده)

وظایف اضافی DDBMS: 

mindmap

      Commit دوفازی
    شفافیت
      پنهان کردن توزیع
      ترکیب نتایج
    بهینه سازی
      کاهش تاخیر شبکه
      انتخاب بهترین سایت

🔀 نا همگنی (Heterogeneity)

نکته مهم : "در این معماری اجزا می‌توانند ناهمگن باشند (بر خلاف C/S)"

جنبهC/SDDB
DBMSباید یکسان (همگن)می‌تونه متفاوت (ناهمگن)
OSباید یکسانمی‌تونه متفاوت
سخت‌افزارباید یکسانمی‌تونه متفاوت
مثال DDB ناهمگن: 
سایت تهران: Windows + SQL Server + HP Server
سایت لندن: Linux + PostgreSQL + Dell Server
سایت نیویورک: Unix + Oracle + IBM Server

→ همه با هم کار می‌کنن! ✅ (با DDBMS قدرتمند)

چرا این یک مزیت بزرگه؟

  • می‌تونی از بهترین DBMS برای هر سایت استفاده کنی
  • انعطاف‌پذیری بالا
  • می‌تونی سیستم‌های قدیمی رو ادغام کنی

خودمختاری یعنی:

  • هر سایت می‌تونه تصمیمات محلی بگیره
  • هر سایت می‌تونه برنامه‌های محلی اجرا کنه
  • هر سایت می‌تونه داده‌های محلی مدیریت کنه

ولی:

  • برای تصمیمات سراسری → نیاز به هماهنگی با Master Site
  • برای Transaction توزیع شده → نیاز به Coordinator

✅ مزایای DDB

1. مقیاس‌پذیری بالا

نیاز به ظرفیت بیشتر؟
→ فقط یک سایت جدید اضافه کن! ✅

متمرکز: باید سرور بزرگ‌تر بخری (محدود!)

2. قابلیت اطمینان بالاتر

اگر سایت تهران down بشه:
→ سایت‌های دیگه همچنان کار می‌کنن ✅
→ فقط داده‌های ایران در دسترس نیستن

متمرکز: کل سیستم down می‌شه ❌

3. عملکرد بهتر

کاربر تهران → داده محلی تهران (سریع! ⚡)
کاربر لندن → داده محلی لندن (سریع! ⚡)

متمرکز: همه به یک سرور → کند 🐌

4. خودمختاری محلی

سایت تهران می‌تونه:
- قوانین محلی خودش رو اعمال کنه
- زبان فارسی رو پشتیبانی کنه
- ساعات کاری ایران رو رعایت کنه

5. انعطاف‌پذیری

می‌خوای سایت جدید اضافه کنی؟ ✅
می‌خوای یک سایت رو upgrade کنی؟ ✅
می‌خوای DBMS یک سایت رو عوض کنی؟ ✅

همه امکان‌پذیره!

❌ معایب و چالش‌های DDB

1. پیچیدگی بسیار بالا

باید مدیریت کنی:
- چند سایت
- چند DBMS (شاید متفاوت)
- شبکه‌های پیچیده
- توزیع داده
- Transaction توزیع شده
- Replication
- Consistency

→ نیاز به تیم خبره! 💰💰💰

2. هزینه بالا

هزینه‌ها:
- چند سرور
- شبکه قوی
- DDBMS گران
- تیم بزرگ
- آموزش

3. مشکلات امنیتی

چند سایت = چند نقطه حمله ممکن
→ باید همه رو امن کنی

4. Consistency

اگر داده کپی شده باشه:
سایت تهران: Balance = 1000
سایت لندن: Balance = 1000

تراکنش در تهران: Balance = 900
تراکنش در لندن: Balance = 800

کدوم درسته؟! 😱

→ نیاز به الگوریتم‌های پیچیده Consistency

5. تاخیر شبکه

Query سراسری:
→ باید داده از چند سایت جمع بشه
→ تاخیر شبکه × تعداد سایت‌ها
→ می‌تونه کند باشه

تمرین 1 (تشریحی):

5 نوع شفافیت در DDB را با یک مثال واقعی از یک شرکت چندملیتی توضیح دهید.

تمرین 2 (تستی):

کدام گزینه درست است؟

الف) در DDB، کاربر باید محل داده را بداند ب) DDB می‌تواند ناهمگن باشد ج) DDB ساده‌تر از C/S است د) در DDB، خودمختاری کامل امکان‌پذیر است

تمرین 3 (طراحی):

یک دانشگاه با 5 پردیس در شهرهای مختلف می‌خواهد سیستم یکپارچه بسازد:

  • پردیس 1 (تهران): 20,000 دانشجو
  • پردیس 2 (شیراز): 15,000 دانشجو
  • پردیس 3 (تبریز): 10,000 دانشجو
  • پردیس 4 (اصفهان): 12,000 دانشجو
  • پردیس 5 (مشهد): 8,000 دانشجو

طراحی کنید:

  1. معماری DDB مناسب
  2. چه داده‌هایی را در هر سایت ذخیره می‌کنید؟
  3. چه داده‌هایی باید Replicate بشن؟

تمرین 4 (مقایسه):

جدول مقایسه کاملی بکشید بین:

  • Multi Client / Multi Server (C/S)
  • Distributed Database (DDB)

از نظر: شفافیت، ناهمگنی، خودمختاری، پیچیدگی

تمرین 5 (سناریو):

شما مشاور یک بانک بین‌المللی هستید. بانک شعبه در 50 کشور دارد.

سوالات:

  • کدام معماری پیشنهاد می‌کنید؟ چرا؟
  • چه چالش‌هایی وجود دارد؟
  • چگونه 5 نوع شفافیت را تامین می‌کنید؟
  • چگونه Consistency را حفظ می‌کنید؟

تمرین 6 (تحلیلی):

چرا در DDB خودمختاری کامل غیرممکن است؟ نقش Master Site چیست؟ 3 مورد که نیاز به هماهنگی مرکزی دارند بیاورید.
